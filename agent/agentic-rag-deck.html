01 · Learning map

入门与进阶

一条主线，两种收获

先看懂，再知道该往哪里加能力

所有页面围绕一个问题展开。系统怎样从用户的一句话，走到一份有证据、能核验、必要时会拒答的回答。

你不需要先记住十二个节点。
先记住五次关键判断。

A

刚入门 RAG

看懂切分、检索、上下文和引用怎样连起来。

B

准备做 Agentic

掌握路由、检索计划、证据判定、重试和评测。

02 · RAG basics

先打地基

普通 RAG 只有四个动作

这条链路已经能解决很多问题。后面增加的能力，都在修补它暴露出来的具体失败。

01

切分与索引

把文档拆成可检索的 chunk，并保存来源身份。

02

检索

把问题变成查询，从知识库取回候选证据。

03

组装上下文

挑出少量相关内容，交给生成模型阅读。

04

回答与引用

根据上下文回答，并把结论连回真实来源。

入门先记住　RAG 的价值来自外部证据。模型负责表达，知识库负责提供可核验的事实。

03 · Failure modes

问题驱动升级

Top K 能返回结果，却不保证回答可靠

企业语料里最常见的风险很具体。Agentic RAG 的价值，就藏在这些失败的处理方式里。

弱
证据很像，但不够回答相似度高，只能说明文本接近。
混
同一文档多个版本串在一起回答把 v2.6 与 v3.0 的规则拼成一份。
歧
术语在不同团队含义不同检索方向在第一步就偏了。
假
引用标记查不到来源模型生成了一个看起来合理的编号。

普通检索只回答

哪些内容和问题相似

可靠系统还要回答

这些证据是否足够且可用

04 · Agentic upgrade

五次关键判断

Agentic RAG 给检索链路加上决策与反馈

Agent 在边界内选择下一步，过程留下 trace，证据不足时结束或重试。

① 听懂问题意图、术语、版本、权限可澄清或拒绝
② 规划检索选工具，决定改写或拆解
③ 找并排序混合召回，去重，再精排
④ 判断证据检查覆盖与强度可补查或拒答
⑤ 生成并校验回答、引用、终态检查
↺
闭环来自反馈　证据判定会告诉检索计划缺了什么。重试有次数上限，也必须带来新证据。

05 · Control boundary

设计分工

让模型处理模糊，让代码守住边界

自然语言需要模型理解。权限、工具范围和版本过滤需要稳定、可测试的规则。

LLM 更擅长

理解用户在说什么

  • 识别意图与主题
  • 改写口语问题
  • 拆解多方面问题
  • 给出自然语言回答
＋

代码必须拥有

决定系统能做什么

  • 权限与工具允许列表
  • 版本和 metadata filter
  • 重试次数与停止条件
  • 引用解析与终态校验
工程判断　模型输出进入工作流前，先经过 schema、枚举和值域校验。失败时走可观察的安全回退。

06 · Understand and route

第一次关键判断

检索之前，先固定问题的边界

这一步做错，后面的向量检索越强，偏得越快。

1
需要查知识库吗打招呼、显式记忆和操作请求可以直接分流。
2
用户说的术语指什么歧义无法消除时，请用户澄清。
3
要看哪个版本默认 current，明确指定时 exact，对比时 comparison。
4
用户能访问哪些资料权限检查发生在任何私有检索之前。

示例

“GO 按钮在 3.0 里怎么配置？”

entity · GO 按钮version · v3.0intent · how_toscope · product docs

解析结果会变成检索参数，也会一路保留到引用。

07 · Retrieval plan

第二次关键判断

查询转换要有边界，也要解释得清

每轮只选一种主策略，可执行查询最多三条。所有派生查询继续遵守原来的权限、实体和版本范围。

01 · identity

原样检索

问题已经清楚，保留原词和约束。

02 · rewrite

改写

把口语和别名改成更适合检索的表达。

03 · step back

补背景

为机制问题增加背景查询，同时保留原问题。

04 · decompose

拆问题

把对比或多方面问题拆成两到三条。

工具选择　Agent 只调用最小相关工具集。检索回来的文本属于不可信数据，无权改变过滤器或申请更多工具。

08 · Hybrid retrieval

召回层

语义、关键词和过滤器各管一件事

混合检索的目标是把候选找全。它不会替代后面的精排与证据判定。

Dense lane

找语义相近

适合自然语言改写、同义表达和概念问题。

＋

BM25 lane

找精确词项

适合产品名、错误码、版本号和专有名词。

→

Filter first

守住范围

部门、文档类型、权限与版本先下推，再合并候选。

合并

按稳定的 chunk_id 去重，并保留每次命中的来源。

扩展

穷举型问题可有界地补充同一文档的相邻证据。

记录

每轮计算证据池指纹，用来判断重试有没有进展。

09 · Evidence pipeline

第三次关键判断

召回、精排、判定是三份不同的工作

把三层拆开，系统才知道问题出在没找到、没排好，还是证据本来就不够。

Recall

尽量找全从大语料里取回一批候选，允许有噪声。
→

Rerank

按相关性排序把同一批候选完整重排，选出少量上下文。

Evidence grader

回答前再问一次
够不够

  • 是否覆盖问题的每个方面
  • 对比问题两侧是否都有证据
  • 证据是否来自允许的工具与版本
  • 弱证据是否应该触发补查或拒答

10 · Bounded retry

证据闭环

重试必须带来新证据

证据判定会给出缺口，规划器据此补查。循环有上限，也有更早的停止条件。

01发现缺口缺版本、缺对比侧、证据太弱
02生成补查计划保留原问题的产品名与约束
03执行并合并新候选进入同一证据池
04再次判定回答、继续或明确拒答
最多 3 轮 · 重复查询提前拦截 · 证据池不变立即停止
正确终态　“现有资料不足以回答”是一种正常结果。系统到达边界后继续猜，才是故障。

11 · Grounded answer

第四次关键判断

回答只有通过引用校验，才能离开系统

模型只能使用工作流分配的引用标记。每个标记都要解析回本轮真实选中的 chunk、页码和版本。

Milvus 3.0 的文档同步流程先从对象存储读取文件，再按发布配置切分并写入知识库[C1]。默认检索只使用当前版本，版本对比需要显式改变作用域[C2]。
✓
校验通过后分块释出　空输出、无引用、越界标记和版本混用都会触发回退。
C1 · chunk_0184ingestion.md · page 4 · v3.0 · checksum verified
C2 · chunk_0241versioning.md · page 2 · v3.0 · current edition

稳定身份

doc_id
＋ doc_version
＋ chunk_id

12 · Memory and cache

扩展能力

历史、答案复用和知识证据各有边界

三者放在一起最容易误用。记住它们各自回答的问题，就不会把旧对话当成事实来源。

Conversation memory

用户刚才说过什么

补全指代，列出最近问题，保存显式记忆。按 session 和 TTL 隔离。

不能充当知识库引用
Grounded cache

这个问题以前答过吗

相似度只负责找候选。复用前仍要复核权限、版本、checksum 和 KB revision。

命中可跳过检索与生成
Knowledge base

当前事实由什么支撑

保存可引用的文档证据，版本与权限过滤始终生效。

负责支撑最终结论

13 · Milvus in the loop

能力地图

Milvus 承担检索，也承担一部分边界

入门先掌握前三项。后面的能力根据数据形态与失败案例逐步引入。

Dense ＋ BM25同时覆盖语义表达与精确词项。
Scalar filter把版本、部门、类型和权限范围下推到检索。
稳定 chunk 身份让候选合并、缓存复核与 citation 能对齐。
TTL 与时间字段支持会话、缓存和选择性记忆的生命周期。
StructArray 与 EmbeddingList在长文档内部定位 passage，同时保留文档身份。
排序与聚合为业务顺序、候选 facet 和软遗忘提供原生能力。
选择原则　先用最便宜的检索层级跑基线。只有观测到的失败能证明收益时，再增加索引、向量 lane 或文档级投影。

14 · Retrieval ladder

进阶选择题

复杂度要由失败案例来购买

Workshop 默认展示 hybrid，是教学选择。真实项目要比较更简单的方案，记录质量、延迟和迁移成本。

T0最低成本

BM25

语料小、术语稳定时，先验证 lexical retrieval 能否满足需求。

T1理解升级

查询转换与实体目录

处理口语、别名和多方面问题。

T2检索升级

Dense ＋ BM25

语义和精确匹配互补，代价是 embedding 与双路索引。

T3 至 T5生命周期升级

按需、冷热或全量

根据语料变化速度与访问分布选择 embedding 策略。

15 · Evaluation

第五次关键判断

评测要能指出第一处失败

总分告诉不了你该改哪里。一次请求要沿着轨迹、工具和结果三层定位。

Trajectory
阶段顺序是否合法，是否在正确位置停止
Tool
工具、查询、过滤器和版本范围是否正确
Outcome
事实覆盖、引用解析、拒答和版本隔离是否正确

最小质量指标

  • Recall@K 与 selected context recall
  • required fact coverage
  • citation resolve rate
  • abstention correctness

维护纪律

  • 先读真实 trace，再决定长期指标
  • 每个失败和修复一起进入 fixture
  • 一次实验只改变一个变量
  • 延迟和成本单独看，不与质量混分

16 · Build path

建议实践顺序

先做出可信主链路，再增加 Agent 能力

每一步都留下可运行结果和验收条件，避免一次把所有能力堆进工作流。

STEP 1RAG 基线

可解析引用

一条 golden question 能检索、回答，并解析到真实 chunk。

STEP 2可观察

Trace 与证据

展示分类、工具、召回、精排和最终上下文。

STEP 3有边界

路由与判定

加入术语、版本、权限和 evidence grader。

STEP 4形成闭环

补查与评测

实现受限重试、拒答、fixture 和回归门禁。

17 · Takeaways

收束

可靠的 Agentic RAG，靠的是一条能解释、会停止、可复现的证据链。

01

模型负责理解

代码负责权限、范围、重试和校验。

02

检索负责找全

精排负责排序，grader 负责判断够不够。

03

复杂度要有证据

从最小基线开始，用失败案例决定升级。

最后检查　引用能否回到真实来源，证据不足能否拒答，失败能否在 trace 里找到第一处原因。
